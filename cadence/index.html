Cadence

Every GST return provably right before anyone signs it — the errors found by the ledger's own history, not by a human reading 1,400 lines at 9pm.

Cadence reads a client's Xero data each period, generates the exceptions from that client's own learned coding history, and produces a workpaper where every figure traces to the transaction that made it and every judgement carries a named human's signature. Xero already computes and files the NZ GST return — the work Cadence replaces is proving it right beforehand, which Colab Accountants currently does in a Google Sheet across ~50 client organisations. Coreshift builds, hosts and operates it on the practice's behalf for a retainer.

The Three Goals

🔍
Generate the findings
Not a checklist to fill in — the exceptions come out of the client's own reconciled coding history, ranked by confidence, with the evidence attached. This is the one thing neither Xero nor a workpaper tool does.
🧾
Every number carries its source
Any figure on the return drills to the transactions behind it. A figure that can't be traced renders as "unverified", never as a number — and a return with an untraceable box can't be signed.
✍️
A named human signs, always
Resolve or accept each exception with a written reason; signing locks and hashes the workpaper. Auto-filing without a signature is a permanent boundary, not a deferred feature.

Phase 0 Evidence
In progress · M2–M3 · no code

Two milestones with no software in them, deliberately. The largest risk in this project is building the exception ruleset from assumptions instead of from Colab's actual process — so the catalogue comes off their live Google Sheet and their timed returns, and the reviewer signs a hand-made workpaper before a line of product code exists.

  • Colab's live GST sheet analysed into a written exception catalogue
  • Client list segmented vanilla vs complex, with counts
  • Five real returns timed by activity — computing vs chasing
  • GST101A box set and arithmetic verified against IRD's current form
  • Reviewer signs our hand-made workpaper on ≥7 of 10 returns

Starts after M3 · M4–M8

Foundation on our own database and our own Xero connection, then the coding-profile engine that everything downstream depends on, then the GST computation, the exception sweep, and the traceable workpaper a reviewer will sign.   • GST101A boxes computed from journals, tying to the cent
  • Ranked, evidenced exception list worked without opening Xero
  • Immutable, fully traceable workpaper signed by a named reviewer

Phase 2 Operate it
Starts after M8 · M9–M10

Filing through Xero's existing IRD connection, then the whole book running unattended on a schedule with Coreshift's touch limited to genuine exceptions. This is where the retainer either works or doesn't — the metric that matters is Coreshift minutes per return, not features.

  • Signed returns file via Xero with the acknowledgement captured
  • A full cycle runs unattended, ≥95% per-client success
  • Operator console: what ran, what failed, what needs a person
  • Backup/restore drill passed before the sheet is retired
  • Colab stops maintaining the Google Sheet

✓
📐 M1 — the idea, pressure-tested and reframed before a line of code
Ran the full ideation workflow. **Verdict: Strong, 25/30** — but the framing had to change to get there. The brief was "end-to-end GST filing"; validation established that **Xero NZ already computes the GST return and already files it to IRD**, so building that would rebuild something Colab gets free. The labour is everything that must be true *before* anyone presses the button — miscoded lines, wrong tax rates, unreconciled bank items, period-boundary strays, unexplained movement, records the client hasn't sent — and because the Google Sheet holding that checklist proves nothing, **the reviewer re-derives every return from scratch. Colab pays for the review twice.** So the product is the exception sweep + traceable workpaper + named sign-off, and filing is a feature on the end. **Three fatal flaws ranked with fast tests**, the sharpest being that the core assumption is still unverified: if the hours actually go into chasing clients rather than checking coding, the engine automates the cheap half and headcount doesn't move — which is why M2 and M3 contain no software. **Competition mapped honestly**, including the one that matters: Xero's own rebuilt Workpapers with a GST worksheet landing this year, bundled, from a vendor with far more resource than us. Six documents written: `product-idea.md`, `validation-report.md`, `VISION.md` (validated field-by-field against the skill's template by script), `product-vision.md`, `prd.md` (10 tables, 4 database-level integrity triggers, 22 endpoints, 25 functional requirements, 8 open questions each with a recommendation), and `product-roadmap.md`. **Two premises are labelled unverified throughout rather than quietly assumed:** the GST101A box map is *not* implemented from memory — it gets verified against IRD's live form first — and the 11-rule exception catalogue is explicitly a **hypothesis** to be rewritten from Colab's actual sheet in M2
✓
🗄️ The feasibility spike, harvested and archived
`core-ricky/cadence` was **a prototype built to prove a function was possible, not a foundation** — 43 commits in one week (2026-06-15 → 06-22), then dormant two months. It read like a shipped product (multi-tenant schema + RLS, a V1 dashboard with Prep → review attention → Run for real, team invites, the truth-sync reconcile loop, bulk post-back) and was initially planned as the thing GST would extend. Ricky's correction — it was a muck-around — changed the call, and **the clean rebuild is strictly better than the merge would have been.** A fresh Supabase project deletes the entire coupling problem at once: the additive-only migration constraint, the `verify-scope.ts` CI guard, the shared-schema review burden, **and** the single-use-Xero-refresh-token race between two services reading one token table. Nothing runs in parallel, so there's no half-finished port to strand. Renamed to **`cadence-spike`** and archived read-only, with a superseded banner pointing here; the *name* Cadence was kept for the product because a good name shouldn't go in the bin with the code. **Harvested as knowledge, not code:** the confidence rule (`consistent` / `conflicted` / `rare`), the payee-key normalisation, the proven result (8 of 26 lines auto-reconciled correctly, Woolworths/Kmart correctly deferred as conflicted), the schema shape as reference, and the operational lessons — truth-sync, the progress watchdog, payee grouping, Railway's `npm ci` optional-dep failure, the middleware relative-`Location` 500. **🔴 One honest cost of the clean break:** the exception engine's baseline was going to be the spike's live `coding_profiles`. It doesn't exist on a fresh build, so **the profile engine is now in scope as its own milestone (M5)** — previously assumed free. It's a fraction of the spike's scope, though: GST needs the *profile learning*, not the reconcile-and-auto-post machinery

Real value and a plausible second module later — but carrying it now would double the build for no GST benefit. The spike proved it works (8/26 auto-reconciled correctly); that knowledge is banked
Billing / Stripe

The spike anticipated it; this product explicitly doesn't. The retainer is invoiced directly, so there are no payment rails, no billing UI and no PCI surface. Revisit only if Cadence is ever sold self-serve to multiple practices
Client chase portal
parkedcontingent
Chasing clients for missing records may be a real share of the cycle. **If M2's timing shows chasing dominates, this stops being parked and becomes the pivot** — a different, cheaper product than the one currently planned
Writing corrections back into Xero
parked
The preparer's natural next action after seeing a miscoded line, and bouncing to Xero is real friction. Deferred because writing to a client's ledger is the highest-consequence action available and needs trust the product hasn't earned. Reconsider after M8, behind explicit per-action confirmation
Complex-basis and adjustment-heavy clients
parkedscope
Payments and hybrid basis, private-use and entertainment adjustments, imported goods, zero-rated land, secondhand goods, bad debts, GST103 provisional-tax coupling. Each is a distinct ruleset. Declined **by design and in writing** rather than discovered as failures mid-cycle — which Coreshift can only do because it owns the asset. Unlock per category, ranked by how many client files each actually serves

CSV / data export
parkedsecuritygst_transactions
