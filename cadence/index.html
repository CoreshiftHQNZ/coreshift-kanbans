Cadence

Every GST return provably right before anyone signs it — the errors found by the ledger's own history, not by a human reading 1,400 lines at 9pm.

Cadence reads a client's Xero data each period, generates the exceptions from that client's own learned coding history, and produces a workpaper where every figure traces to the transaction that made it and every judgement carries a named human's signature. Xero already computes and files the NZ GST return — the work Cadence replaces is proving it right beforehand, which Colab Accountants currently does in a Google Sheet across ~50 client organisations. Coreshift builds, hosts and operates it on the practice's behalf for a retainer.

Next milestone Ground truth captured No date — milestone-based

The Three Goals

🔍
Generate the findings
Not a checklist to fill in — the exceptions come out of the client's own reconciled coding history, ranked by confidence, with the evidence attached. This is the one thing neither Xero nor a workpaper tool does.
🧾
Every number carries its source
Any figure on the return drills to the transactions behind it. A figure that can't be traced renders as "unverified", never as a number — and a return with an untraceable box can't be signed.
✍️
A named human signs, always
Resolve or accept each exception with a written reason; signing locks and hashes the workpaper. Auto-filing without a signature is a permanent boundary, not a deferred feature.

📐 M1 — the idea, pressure-tested and reframed before a line of code
Ran the full ideation workflow. **Verdict: Strong, 25/30** — but the framing had to change to get there. The brief was "end-to-end GST filing"; validation established that **Xero NZ already computes the GST return and already files it to IRD**, so building that would rebuild something Colab gets free. The labour is everything that must be true *before* anyone presses the button — miscoded lines, wrong tax rates, unreconciled bank items, period-boundary strays, unexplained movement, records the client hasn't sent — and because the Google Sheet holding that checklist proves nothing, **the reviewer re-derives every return from scratch. Colab pays for the review twice.** So the product is the exception sweep + traceable workpaper + named sign-off, and filing is a feature on the end. **Three fatal flaws ranked with fast tests**, the sharpest being that the core assumption is still unverified: if the hours actually go into chasing clients rather than checking coding, the engine automates the cheap half and headcount doesn't move — which is why M2 and M3 contain no software. **Competition mapped honestly**, including the one that matters: Xero's own rebuilt Workpapers with a GST worksheet landing this year, bundled, from a vendor with far more resource than us. Six documents written: `product-idea.md`, `validation-report.md`, `VISION.md` (validated field-by-field against the skill's template by script), `product-vision.md`, `prd.md` (10 tables, 4 database-level integrity triggers, 22 endpoints, 25 functional requirements, 8 open questions each with a recommendation), and `product-roadmap.md`. **Two premises are labelled unverified throughout rather than quietly assumed:** the GST101A box map is *not* implemented from memory — it gets verified against IRD's live form first — and the 11-rule exception catalogue is explicitly a **hypothesis** to be rewritten from Colab's actual sheet in M2

📏 The GST101A box map, verified from IRD's own form — and four things the PRD didn't anticipate
TASK-006 done, and the 🔴 "do not implement from memory" warning is discharged the right way: the forms were downloaded from IRD and text-extracted, then cross-checked against **IR375 (March 2026)**, the current edition of IRD's own guide. **The PRD's indicative numbering was correct** — Boxes 1–4 identification, 5–15 the return, with every derivation confirmed verbatim (`7 = 5−6`, `8 = 7×3÷23`, `10 = 8+9`, `12 = 11×3÷23`, `14 = 12+13`, `15 = |10−14|`). Four findings change the build: **(a) Boxes 9 and 13 are not ledger-derivable at all** — both read *"from your calculation sheet"*, i.e. manual GST adjustments — so they default to `traceable=false`, **and Boxes 10, 14 and 15 inherit non-traceability whenever either is non-zero.** The lower half of the return is only as traceable as its weakest input, and the engine has to propagate that. **(b) Imported goods are excluded from Box 11** and claimed as a Box 13 credit adjustment (IR375 p.33: *"Do not include imported goods under purchases on your GST return"*) — that is a real exception rule with a hard IRD citation and a likely error in a Xero-coded ledger, banked as `IMPORT_IN_BOX_11`. **(c) Box 15 is a magnitude plus a direction**, `refund`/`to_pay`/`nil` — a signed number can't render the form and silently loses the nil case. **(d) GST103B Part 1 is byte-for-byte the GST101A return**, so `return_type` decides whether Parts 2–3 apply, not which box map to use — **one engine serves both**, a real simplification to M6. Resolves `prd.md § 14 Q4`. Also recorded: **IR372 is a dead end** — the only published version is August 2010 and IRD files it under *"before 1 April 2011"*; IR375 Part 4 is the live authority on adjustments
✓
📊 The coding-profile baseline is feasible — measured, not hoped
The honest cost of the clean break was that M5's baseline no longer came free, and it was unknown whether Colab's ledgers could even support learning one. **They can.** Measured across **277,595 real transaction lines from 139 client ledgers**: **61.9% of lines sit under a payee with a single dominant historical coding, and only 8.2% have no baseline at all.** 129 of 139 clients (93%) have five or more consistent payees; **none have zero**; median 37 per client. 🔴 **The trap worth recording: weighted by *payee key* the consistent share looks like 26.5%** — because keys are dominated by a long tail of one-off suppliers. That understates real coverage by more than 2×, and quoting it would have made M5 look far weaker than it is. So `prd.md` FR-010's *"a client with no profile cannot be swept"* turns out to exclude essentially nobody. 🔴 **But the provenance is the finding that matters more:** every one of the 147 client records carries a `manual-*` tenant id, and `xero_connections` and `xero_tokens` are **both empty** — **the spike never made a single Xero API connection.** The data came in through a browser extract. That means field shapes will differ after a real API pull (`tax_type` as a proper enum rather than the UI label `"GST"`), the numbers must be re-measured in M7 rather than carried forward — and, per the Xero email above, the extract route itself is now in question. The 29.9% of lines under `conflicted` payees isn't a failure either; it's where the precision target gets won or lost

Also banked: a hand-written **entertainment threshold at $57.50** (50% GST-deductible in NZ, so miscoding it produces a wrong return — ⚠️ verify the figure against IRD first), a payee **suppression** rule the catalogue has no concept for yet, and `No bank feeds` as the preparer's most-repeated real-world problem. ⚠️ **It's a June export, not the live sheet** — counts drift (167 vs 158) — so every figure is provisional

🔴 **Correction: it is not an email.** The Gateway Customer Support Portal is only reachable *after* an organisation registration is assessed and approved, and there is no pre-registration email address published anywhere on ird.govt.nz — IRD's own answer to "who do I ask" is *"your relationship manager will guide you"*, and you only get one by registering. **The action is a form:** `gws.ird.govt.nz` → *Organisation Registration – Gateway Services*. **It's a better instrument than the email would have been:** two of the three questions are structured fields on it, so the arrangement gets *declared* to the assessor who decides rather than queued as an enquiry.
