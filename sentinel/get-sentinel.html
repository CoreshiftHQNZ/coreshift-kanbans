Get Sentinel on your project

Every Coreshift build — app or website — ships with Sentinel monitoring. You can onboard yours yourself; you don't need to go through Abe to start.

Sentinel is Coreshift's monitoring layer: uptime, security auditing, and a support path, contractually promised on every build. This page is how anyone at Coreshift gets it onto their project. It takes about 10 minutes of your time; the rest is wired for you.

1 · Which track are you?

Website build

Static marketing site

  • Cloudflare Pages, no database, no logins
  • e.g. a brochure / lead-gen site
  • Sentinel gives: uptime + a weekly endpoint security audit
Product / app

App with accounts + data

  • Railway + Supabase
  • Has users, a database, server logic
  • Sentinel gives: the full picture — advisor scans, uptime, error monitoring, bug intake

Not sure? If it has logins or stores user data, it's an app. If it's a static site with just a contact form, it's a website.

2 · Register it in Sentinel yourself

A

Open Sentinel and onboard

Go to sentinel.coreshifthq.com/maintenance, sign in with your Coreshift Google account, and click Onboard an app. Fill in the slug, display name, and GitHub repo.

Website builds: choose Website and enter your Live URL — that's the address the weekly endpoint audit points at. That's all Sentinel needs to start auditing it; no code scan, no database.

3 · Make your repo Sentinel-ready

Do this in your own repo — paste the block for your track into a Claude Code session opened in that repo. It sets up the security + observability baseline so Sentinel finds a clean project.

App track — paste this into Claude Code

Bootstrap <app-slug> to Coreshift's secure + observable baseline before feature work:
1. Supabase — RLS deny-by-default on every new table from the first migration; turn
   on HIBP leaked-password protection (prod + staging). Both are Coreshift standards.
2. Sentry — create <UPPER>-BACKEND + <UPPER>-FRONTEND projects in the coreshift-hq
   org; wire the DSNs + environment tags.
3. Heartbeat — add a GET route that reads ?marker and calls Sentry.captureMessage,
   guarded by a shared SENTRY_HEARTBEAT_TOKEN header.
4. Report Issue widget — add it pointed at KC's report-issue Edge Function with
   appId: "<app-slug>".
5. Env vars — the Sentry DSNs, SENTRY_HEARTBEAT_TOKEN, and the report-issue endpoint,
   on staging + prod.
Goal: by first deploy the app reports errors, answers a heartbeat, accepts bug reports,
and passes the advisor baseline.

Website track — the checklist

  • Add a _headers file (HSTS + CSP + nosniff + frame + referrer). Copy-paste starter: Cloudflare Pages security-headers recipe — roll CSP Report-Only first, then enforce.
  • Contact form behind Cloudflare Turnstile (both the secret and the widget).
  • CI deploy on push (GitHub Actions → wrangler pages deploy).
  • Then register in Sentinel with the live URL (step 2). The weekly endpoint audit picks it up automatically — no widget needed; your contact form is the support intake.

4 · What ops wires for you (you don't chase anyone)

A few steps need someone with admin access or the Privacy Officer. You don't need to ask for them — when you register, Sentinel automatically creates an onboarding checklist on your project's card (under Maintenance) listing every remaining step and who owns it. Ops and the Privacy Officer tick off theirs; you can watch the status there:

What you get

Once you're registered and live: a per-app view in the Sentinel dashboard, uptime alerting, a weekly security audit (endpoint hygiene for websites, advisor scans for apps), and — for apps — error monitoring and a bug-report → GitHub-issue path. Support runs 9am–5pm NZ.
