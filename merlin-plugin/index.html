P2wire · TASK-022 · 0303 Aug

Two things Merlin was never recording — and a measurement that quietly became a different measurement

Keitha named a number this build could not produce: how much of the work a person brings themselves, rather than Merlin proposing it. That is the one that shows somebody becoming independent, and nothing on the wire held it — a piece of work recorded what kind of work it was and never whose idea it was. It does now, as one of three: they arrived with it, they picked it off Merlin’s list, or Merlin raised it unprompted. Neither field could have been added later. A start is recorded the moment work begins and that moment is gone, and a starting point cannot be reconstructed after somebody has already improved — so every session run without them lost the data permanently, which is why this went in ahead of the next planned task rather than inside it.

The second field is a correction, and the correction is the more interesting half. Intake has always asked whether someone has used AI before, and the answer became a number every later confidence reading is measured against. But the question the brief actually asked was how they felt, and what the number scores is what they do. Those are different things about the same person — somebody can use AI daily and dread it — and the difference had been written down, in bold, in two separate files, each with a reasoned argument for why it was fine. Keitha ruled the argument moot on 3 Aug: the same person answering the same question at both ends is trivially consistent, and the self-report was always what was wanted. So intake now records both, permanently, and nothing anywhere subtracts one from the other or draws them as one line. A person is allowed to be experienced and unconfident.

Why it survived four days of being noticed is the part worth keeping. A mismatch mentioned in passing looks like an oversight and gets fixed. A mismatch argued for at length reads as a decision — and nobody re-litigates a decision. Four sessions each read the note, each concluded it had been thought about, and each built on it, until the drifted reading was load-bearing in a database view, a live endpoint, the test fixture and the file that says what the dashboard should show. No test could have caught it: every layer agreed with every other layer, and each was honest. The only thing that catches this is somebody holding the original brief and reading the field’s own description out loud. The learner never hears either number, and there is never a number in the conversation — both mappings are Merlin’s, and the question about how they feel is asked about the work rather than about them.

P5TASK-0463 Aug

The manager’s reads — and a guarantee that turned out to be an empty room

A promise this build has made since day one is that a person cannot reach their team’s data. Two separate test suites had been checking it for weeks, and neither was checking anything. Both asked the manager endpoint for team data using an ordinary learner’s credentials and confirmed it came back refused — but the endpoint did not exist yet, so what came back was “no such page”. An absence that reads exactly like a refusal. One of the two said so in its own comment: the absence is the guarantee, and this test exists so that adding one without a permission check fails here first. It did fail, on the first run after the endpoint was built, which is the alarm working rather than breaking. The promise is now genuinely tested — three ways, each paired with a legitimate manager succeeding in the same run, because a refusal test where nobody can see anything passes for the wrong reason, which is a mistake made here a day earlier. The third case is the one that would otherwise have been missed: a real, correctly-signed manager credential belonging to someone since moved back to an ordinary seat. Proven by demoting the person and re-reading with the very same credential.

The trap worth knowing about is that the wrong version of this passes every test. There are two ways for the server to ask the database a question — as the person asking, or as the system. As the system, the manager’s numbers come back correct, sitting alongside twelve hundred other businesses’. Nothing errors, and every figure a test could check is right. So the check is a search of the code itself for the master key, which appears nowhere on this path.

And the endpoint says what it cannot tell you rather than going quiet. Five of the figures the original spec asked for have no source in the data, and each comes back explicitly blank with the reason attached, on the wire, where whoever builds the dashboard will read it. The most interesting is the “confidence improvement” headline: the two numbers it subtracts are different measurements — one is Merlin’s read of how much AI someone already used, the other is how confident they say they feel — so subtracting them makes a confident user look like they got worse. Rather than only refusing, the response carries the fix somebody has to choose: measure from their first self-report instead, the same instrument at both ends, which changes what the dashed line on the designer’s chart is claiming. Half of that fix was built on 3 Aug and the choice is still open — see the card above.

P5TASK-044b · 0453 Aug

The manager’s five views — and the default that would have handed one learner the whole database

A Postgres view runs with its owner’s permissions, not the caller’s. The owner here is the superuser, so a view over the telemetry table returns every business’s rows to anyone who asks — by default, silently, while looking entirely correct. Measured rather than asserted: with the flag off, one learner reads 1,253 team rows, 1,252 of them other businesses. With it on, nought. There were no views in this database before, so this is the migration that sets the habit, and the test removes the flag, records the leak and puts it back so the guarantee can never quietly become a comment. None of it could have been checked a day earlier. No business in the database had more than one person — no six-week history, no seat that went quiet — so a correct view and a broken one were indistinguishable. The fixture built first is ten seats over six weeks carrying the designer’s numbers exactly, and it is deliberately awkward: work that was finished but never formally started, work started and never finished, and two abandoned sessions on one person on one day adding up to thirty hours inside a twenty-four hour day. Every one of those is real pilot behaviour, and each would have been smoothed away by a view built only against the happy path. Two defects came out of running it rather than reading it. One view counted judgements the assessor had explicitly declined to conclude as evidence of progress — the flattering direction, inside the one view whose job is to be honestly empty. And the “recent wins” list could reorder between two identical page loads, because two people finished at the same second and the list cut between them. A third was in the test itself, and is the one worth remembering: it checked that a learner sees no team data, and passed — while a setup mistake meant nobody saw anything, including the manager. A test whose subject is an empty result has to prove someone legitimate gets a full one. What the views deliberately will not say: hours saved, money saved, or anything about competencies. The deck’s lead figure multiplies an hourly rate by hours saved, and nothing anywhere measures hours saved — so the field is empty rather than plausible, and the honest number the data does support is a count of sessions.

P4TASK-041 · 0423 Aug

The invisible step becomes checkable — and three vulnerabilities on the way

A finished piece of work now leaves exactly one record saying the assessment ran, and what it decided. Until this landed it left nothing at all, so a step that ran correctly and a step that never ran were indistinguishable — which is how a bug hid through nine test conversations behind a green build. The planned fix was the wrong shape and the table said so: the record was to go in the competency table, which cannot hold a row that is about no competency. It rides the ordinary activity feed instead, carrying two numbers and no words.

Then the security review, and it found more than the new code. Three things, all fixed. A person could have credited themselves with a competency by hand — now refused, and the reason the old safeguard was believed to prevent it has been corrected rather than repeated, because it never did. And the one that matters: a manager could have made a colleague’s completed work silently disappear — no error, no trace, nothing on either side to notice — using only the team visibility they are meant to have. That flaw was in the database from the first week of the build, on every kind of activity, and it was found by generalising a one-day-old version of it. Proven by replaying the attack against the old design and the new: suppressed before, kept after.

Written down once rather than left to be rediscovered: every number a manager sees is reported by the learner’s own machine, because that machine is the only thing that sees the work — which is the privacy promise, not a hole in it. So the dashboard may honestly say what the team’s machines reported, and not what the team did. At pilot scale, with a manager who knows the people, those are close enough to be useful. Still unproven: whether a real conversation makes the call. That is the next test run, and it is now something a query can answer.

merlin-module on the proven seven-beat anatomy (5–12 minutes, parallel step_hints, a recovery line per step) and merlin-loop’s five-step closure. P1TASK-011 · 01431 Jul

The shared adaptive engine block ✓

Three dials — pace, technical depth, expressiveness — as a shared instruction block every skill includes. Where reassurance lives got settled: it rides on pace, because depth exposes concepts and expressiveness governs how much someone opens up, and neither of those is about comfort. Warmth is the floor and never moves; reassurance is the dial. Stance transitions too: repeated struggle softens, impatience briskens, and anti-lock-in re-stances after one failed adjustment rather than two — two-to-trigger plus two-to-re-stance leaves someone stuck six turns, and a nervous learner has gone by four.

P1TASK-012 · 01331 Jul

Per-user memory + dial persistence ✓

profile.md, pathway.md, ledger.jsonl, outbox.jsonl, in two directories rather than one: recoverable state where auto-loading helps, the irreplaceable record where no consolidator walks. Each dial stores a value, a one-line reason and when it last moved — and the reason is held to a stricter test than surviving the next session: it has to survive being read by the person it is about. Write what someone did, never what they are.

P0TASK-00929 Jul

Sentry on Edge Functions only ✓

Never the MCP server — that runs on the learner’s machine, where a stack trace is an egress path the payload validator never inspects. defaultIntegrations: false is mandatory rather than tuning: the Deno SDK doesn’t instrument Deno.serve, so on a reused runtime one learner’s context can surface attached to another learner’s error. There is deliberately no captureException and no free-form message — the only entry point takes a closed set of enum fields, each checked against a safe pattern, so “never interpolate a rejected value” is a property of the code rather than a rule to remember. Shipped as .mjs rather than .sh: Merlin has to run on Windows, and Node is already required, which also lets the hook reuse the server’s event-id code instead of reimplementing the hash in shell. SessionStart does no network I/O at all — 52ms. Session duration is recorded via a per-session marker so duration_minutes reaches the utilisation metric. cwd is discarded outright; the session id is hashed into the event id and never transmitted.

P0TASK-00729 Jul

Local outbox + merlin_emit_event ✓

Disk first, network later: emit measured at ~40ms and returns before any request is made, so an unreachable backend is invisible to the learner. event_id = sha256(learner_id | type | natural_key) — a random UUID would make every retry a new row, so utilisation and ROI would drift upward on exactly the flaky connections where someone retries most, and nothing would look wrong. natural_key is hashed and discarded, never transmitted, which is what lets the session hook key on a session id without it becoming telemetry. Compaction renames rather than locks, so two concurrent sessions sharing one outbox is safe.

P0TASK-00629 Jul

Ingest + the payload allow-list ✓

No secret key on this path. It connects over the database URL, drops to the authenticated role and sets the claims from the verified token, so RLS enforces rather than an if in the handler. Privilege drops mid-transaction on purpose — the revocation check runs first, because that function isn’t executable by authenticated. The allow-list contains no bare string type: every string derives from the same pattern the database CHECK enforces, so nothing can pass validation and then fail in Postgres. A structural scan runs before schema validation and rejects reflection, evidence, expressiveness_read at any depth, so smuggled content produces a named, alertable rejection. Each row inserts in its own savepoint — without that, one poison event would abort every batch forever and silently end a learner’s telemetry.

P0TASK-00529 Jul

Bundled MCP server ✓

stdio, and fail-soft by contract: missing, expired, malformed and corrupt identity are all states it reports calmly, never exceptions it throws, because a broken tool panel makes Julie think she broke something. The token never reaches a tool result or stderr. The client decodes claims without verifying — it has no key, by design — so that gate is surface reduction for TASK-047, never the permission check.

P0TASK-00429 Jul

Server-issued identity that can’t be forged ✓

HS256 tokens signed with a key held only as a project secret, so the plugin can present an identity but never invent one. The key id is derived from the key material, so rotation needs no bookkeeping. One entry point does signature, claims and revocation together — a caller cannot skip the revocation check — and a registry outage fails closed rather than falling through to “valid”. Failures are enum codes; no rejected value ever reaches a log. The registry stores only the token id, never the token, so a dump of it grants nothing. Verified: self-elevation to owner, impersonation, business switching, alg:none and unknown-key are all refused.

P0TASK-00329 Jul

RLS default-deny on every table ✓

Seven tables, 14 policies, and anon holds zero grants anywhere — there is no unauthenticated surface. Team reads require the token to claim manager/owner and the live row to agree, so demoting someone takes effect on the next request rather than at token expiry, and a stale elevated token stops working immediately. business_id is derived from the learners table, never read from the token: a team-scoped read must never take a caller-supplied business, and a claimed one is still caller-supplied. A manager cannot read rubric-level judgement at all — that is exactly the “individual fumbles” they are never shown.

P0TASK-00229 Jul

Schema — with the no-prose rule as a constraint ✓

Six tables per the PRD, no messages table, and exactly one documented free-text column (nominations.label, present only after an explicit human decision to share). The privacy invariant is a CHECK constraint, not an ingest convention: every payload string must be space-free and under 128 characters, so a sentence cannot be stored at all — a whitelist rather than a length heuristic, because “reject strings over N chars” would still let too_slow_again through as smuggled sentiment. events is append-only by trigger (UPDATE and DELETE raise even for the secret key), event_id must be a hash so a later change can’t regress to random UUIDs, and business_id is stamped from the learner rather than trusted from the request.
