Engine Optimization

The internal tool Growth Partners' SEO specialists run their clients on — audit, plan, do, measure, report, re-plan.

A web app for managing SEO/AEO/GEO clients on a monthly cycle. Everything that can run unattended does: crawls, Search Console and GA4 pulls, AI-citation probes, delta analysis, plan drafting, report drafting. A human signs off before anything touches a client site or reaches a client. The thing that makes it different from every tool we surveyed: it records what we predicted a change would do, then checks — against a control — whether it happened.

Current phase M3 · AI visibility panel
Next milestone A real AI citation, recorded with its raw answer Q3 2026

The Three Goals

🎯
Specialists, not engineers
A team of SEO specialists runs the whole monthly cycle in a web app. Nobody opens a terminal.
🔁
Close the assumption loop
Record what we expect a change to do, then verify it against an untouched control set next month. No prior art does this.
📈
Built for 10, designed for 100
Ten clients today. Multi-client scheduling, per-client history and zero-touch Google access from day one.

✓
Scores that don't drift — and a command that proves it rather than claiming it
The risk carried into this milestone was that two of the tools we surveyed produce audit scores that wander ±10 points on a site nobody touched, which would make every month-over-month claim we build on top fiction. So the scoring was designed backwards from that threat: enumerate every way an unchanged site could score differently twice, then close each one. The ones that mattered — the page set is decided from the sitemap and sorted the same way every time rather than by whichever page answers first; **no rule is allowed to look at today's date**, because a "content updated in the last 90 days" check makes an untouched site score lower every month and the report would call that a regression; a page we couldn't read is dropped from the calculation instead of counted as a failure; and the ruleset is stamped with a version, so if we ever change the weights the app refuses to draw a comparison across the change rather than letting a methodology tweak look like a client result. **Verified by:** `npm run audit -- --client storepro --verify` crawling the site twice and reporting identical results across all 23 checks, plus two separately stored runs both recording 91.50 / 93.44 / 45.45. Reasoning for every rule is written up in `docs/scoring.md`
✓
Found: the audit was confidently wrong twice on its first real run
Both caught and fixed, and both worth knowing because they produced *wrong* answers rather than missing ones, which is the more dangerous failure. **First:** three Storepro URLs return HTTP 200 with a completely empty body. The engine treated them as real pages failing every single check — inventing a shortfall out of an absence, and dragging the scores down with it. A page now only counts as content if an actual HTML document came back and parsed. **Second:** Storepro's team page has an empty `<main>` container with the real content rendered outside it, so the audit read the page as having zero words and reported a perfectly normal page as invisible to AI crawlers. The audit now checks that the section it's reading actually contains text before trusting it. *(The general lesson, and the reason both are recorded: a tool that says nothing is recoverable; a tool that says something false with a number attached is not.)*

Near miss: the DataForSEO check would have reported a false all-clear
The first version of the credential verifier pinged a cheap liveness endpoint before trying anything real. DataForSEO validates the shape of a request *before* it checks who you are, so that ping returned a success response on credentials that were completely invalid — and the verifier would have printed "credentials accepted" while nothing worked. It now makes exactly one probe: the real backlinks call we actually depend on. It also separates "your login is wrong" from "your login is fine but you haven't bought the Backlinks API", because those are different problems with different fixes and DataForSEO sells each API separately. *(Same shape as the M1 trap where Search Console properties list fine and then 403 on every data call. Worth assuming this pattern exists in any vendor API until disproven.)*

Ingestion built on rules that came from other people's failures
M1phase-0shippedsc-domain:
Every design choice traces to a specific observed failure in a surveyed tool, not to taste. **Calendar months, not rolling windows** — a rolling 28-day window anchored to capture time overlaps its own baseline and dilutes every delta. **Totals from a dimensionless Search Console call** — Google anonymises low-volume queries, so summing query rows under-reports; for Storepro's July, 536 of 815 clicks came from queries too small to list, and the app says so on screen. **Both property forms tried** — `sc-domain:` and URL-prefix are different objects with different data, and Storepro has only the URL-prefix form. **"Couldn't measure" never becomes "measured zero"** — a failed source writes no snapshot and records why. **A month can't be ingested until it settles** — Search Console lags ~2 days, so the tool refuses to ingest a month before the 3rd of the next one rather than recording an incomplete month as final

Performance / Core Web Vitals as a fourth pillar
Deliberately left out of the audit score in M2. Measuring it properly needs a rendering engine and real-user field data, and both would put a number that moves on its own into a client-facing score — the exact failure the scoring method was built to prevent. If we want it, it belongs in its own pillar with its own comparability rules
Rendered-DOM comparison
Right now we infer that a page needs JavaScript from what's missing in the raw HTML. Running a headless browser would measure the raw-versus-rendered gap directly and would be a genuinely better diagnosis. It stays out of the *score* even then: a headless browser is the least reproducible thing we could put in one

Briefs, drafts and publishing are a separate concern. Work items can reference them by URL until we know we need more
