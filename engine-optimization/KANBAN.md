- **Scores that don't drift — and a command that proves it rather than claiming it** `M2` `method` `shipped` — The risk carried into this milestone was that two of the tools we surveyed produce audit scores that wander ±10 points on a site nobody touched, which would make every month-over-month claim we build on top fiction. So the scoring was designed backwards from that threat: enumerate every way an unchanged site could score differently twice, then close each one. The ones that mattered — the page set is decided from the sitemap and sorted the same way every time rather than by whichever page answers first; **no rule is allowed to look at today's date**, because a "content updated in the last 90 days" check makes an untouched site score lower every month and the report would call that a regression; a page we couldn't read is dropped from the calculation instead of counted as a failure; and the ruleset is stamped with a version, so if we ever change the weights the app refuses to draw a comparison across the change rather than letting a methodology tweak look like a client result. **Verified by:** `npm run audit -- --client storepro --verify` crawling the site twice and reporting identical results across all 23 checks, plus two separately stored runs both recording 91.50 / 93.44 / 45.45. Reasoning for every rule is written up in `docs/scoring.md`.

- **Found: the audit was confidently wrong twice on its first real run** `M2` `finding` — Both caught and fixed, and both worth knowing because they produced *wrong* answers rather than missing ones, which is the more dangerous failure. **First:** three Storepro URLs return HTTP 200 with a completely empty body. The engine treated them as real pages failing every single check — inventing a shortfall out of an absence, and dragging the scores down with it. A page now only counts as content if an actual HTML document came back and parsed. **Second:** Storepro's team page has an empty `<main>` container with the real content rendered outside it, so the audit read the page as having zero words and reported a perfectly normal page as invisible to AI crawlers. The audit now checks that the section it's reading actually contains text before trusting it. *(The general lesson, and the reason both are recorded: a tool that says nothing is recoverable; a tool that says something false with a number attached is not.)*

- **Storepro's audit baseline — strong technically, weak as an answer source** `M2` `finding` — SEO 91.5 and GEO 93.4 are genuinely good: the sitemap is clean, structured data is present, an `llms.txt` exists, and **no AI crawler is blocked** — all 15 tracked agents including Google-Extended can read the site. AEO at 45.5 is the gap, and it's specific: **not one page** carries FAQ or How-To markup, only half the pages have a heading phrased as a question, and only a third have a list or table an answer engine could lift. **Why that matters here:** it is exactly the profile of a site that gets *read* by AI engines but not *quoted* by them — which is consistent with the M1 finding that Storepro's informational queries hold impressions at position 7–9 while returning zero clicks. Still a hypothesis, and M3's probe panel is what settles it, but the audit and the traffic data now point the same way. **Verified by:** 12 findings stored against run `54b3758e`, each with its evidence and its falsifiability contract.

- **Found: nothing had been loading the local env file since M1** `M2` `infra` `finding` — Every command in the repo used a loader that reads `.env`, a file that doesn't exist here — the secrets live in `.env.local`. M1's commands only ever worked because they were being launched with an explicit flag pointing at the right file, which meant the documented `npm run ingest` failed for anyone following the README from a clean shell. Fixed centrally so every command loads the same way, with real environment variables still winning over files for when this eventually runs on Railway. *(Also found and killed a server left running from a previous session — it was still holding the port and serving old code, which is how this surfaced.)*

- **Near miss: the DataForSEO check would have reported a false all-clear** `M2` `infra` `finding` — The first version of the credential verifier pinged a cheap liveness endpoint before trying anything real. DataForSEO validates the shape of a request *before* it checks who you are, so that ping returned a success response on credentials that were completely invalid — and the verifier would have printed "credentials accepted" while nothing worked. It now makes exactly one probe: the real backlinks call we actually depend on. It also separates "your login is wrong" from "your login is fine but you haven't bought the Backlinks API", because those are different problems with different fixes and DataForSEO sells each API separately. *(Same shape as the M1 trap where Search Console properties list fine and then 403 on every data call. Worth assuming this pattern exists in any vendor API until disproven.)*

## 🅿️ Parking Lot

- **Performance / Core Web Vitals as a fourth pillar** — Deliberately left out of the audit score in M2. Measuring it properly needs a rendering engine and real-user field data, and both would put a number that moves on its own into a client-facing score — the exact failure the scoring method was built to prevent. If we want it, it belongs in its own pillar with its own comparability rules.
- **Rendered-DOM comparison** — Right now we infer that a page needs JavaScript from what's missing in the raw HTML. Running a headless browser would measure the raw-versus-rendered gap directly and would be a genuinely better diagnosis. It stays out of the *score* even then: a headless browser is the least reproducible thing we could put in one.
- **Content production pipeline** — Briefs, drafts and publishing are a separate concern. Work items can reference them by URL until we know we need more.
- **CMS write adapters** — Applying changes directly to client sites (WordPress, Shopify, Webflow, git PR). Approval-gated, and not needed before M7.
- **Multi-agency tenancy** — Built for Growth Partners as a single agency. If Coreshift needs an isolated instance, that's a column plus RLS. Cheap to add later, premature now.
- **API cost accounting** — At 100 clients, per-client API spend becomes real and billable. Worth a table before we get there.
- **Local SEO / Google Business Profile** — Not in scope until a client needs it.
- **Auth for the app** — No login yet; the client view is unauthenticated on localhost. Needed before Railway staging is reachable by anyone else.
- **Calibration study** — After ~12 months we'll have change/prediction/outcome data across every client. That corpus is the moat: it lets us answer "do refreshes on position 8–15 pages actually beat control?" from our own evidence rather than quoting unsourced blog percentages.
