HeyGem

Concierge & errands for Kiwi small businesses — “put a Gem on it.”

Chat-first concierge service: a business texts their Gem (“can you organise team morning tea for Friday?”), the Gem quotes in the chat, the customer approves, the Gem sorts it, and the saved card is charged on completion — followed by a push notification for a star rating, feedback and a photo. One React codebase ships the customer experience as a web app AND native iOS/Android apps via Capacitor; Gems work from a web workspace.

Current phase Core loop complete · seeking first customers
Next milestone First paying customers on the live loop Native mobile deferred

The Three Goals

💬
Text your Gem, it's sorted
Every request is a chat thread per job with auto status and archiving — quote, approve, done, rated.
💳
Charged only when it's done
All-in quote approved in chat; saved card charged off-session on completion, GST receipt sent.
📱
One codebase, every platform
React + Capacitor ships web, iOS and Android from the same app — native push for quotes, completion and ratings.

Every customer-facing policy reads `business_id = current_business_id() OR is_gem()`, so **any** unfiltered customer-side select returns every customer's rows to a `@heygem.co.nz` address — the earlier fix scoped `jobs` and nothing else. Audited all 24 data-access calls across the 17 customer-app source files, plus every RLS policy in `public` and `storage`, plus the two customer-callable Stripe edge functions. **Four more live leaks, all reachable from the Account screen:** `listReceipts()` read `charges` unscoped — every succeeded charge in the system with job number and title, i.e. a full revenue ledger for every customer; `getMyBusinessName()` was `select name limit 1` with **no filter at all**, so for a team address the policy returned every business and `limit(1)` silently picked an arbitrary one with no error to notice — and that name is stamped onto the downloadable **GST tax invoice** as the buyer, so the failure mode was another company's name on a tax document; `getDefaultCard()` and `hasCardOnFile()` read `payment_methods` unscoped, giving another business's card brand/last4 and a card-on-file gate answered from someone else's card. Fixed by making `businessId` a **required parameter** on each helper rather than a filter to remember, so a new call site cannot compile without deciding whose data it wants. **Came back clean:** `stripe-setup-intent` and `stripe-attach-pm` both derive the business from the caller's own profile and never from a request parameter; `JobThread`'s reads are keyed by a job id that only ever comes from the scoped list. The Gem queue now tells a human when a customer is waiting (verified)
M6shippedqueue_alertsnotify-gem-queueLEAD_NOTIFY_TO
**Nothing notified the team that work had arrived.** The only inbound notification in the whole system was the `leads` trigger, and the marketing lead form it fed was removed in `5ac0f5d` — so it had been firing for nothing (the table has never held a row). The Gem workspace learned about new work purely over Realtime, meaning only while a browser tab was open. A real customer filing a request at 6am reached nobody until someone next opened the workspace — the fastest possible way to lose a first paying customer, and the build half of the "who covers the queue" question. Three triggers now raise an alert — new request, customer reply, quote approved — dispatched by a new `notify-gem-queue` edge function that emails the ops address with the business, job number, the customer's own words and a deep link into the workspace. Two things keep it usable rather than noisy: a **debounce**, so four messages in a row produce one email (an alert fires only when a message opens a new stretch of silence from us, with a one-hour escalation floor so a still-waiting customer can re-raise a hand), and a **ledger** — `public.queue_alerts` records the alert *before* the email is attempted, so `where sent_at is null` is a queryable list of alerts that were owed and never delivered, instead of a silent loss. Triggers go through `try_notify_gem_queue`, which swallows every exception: a broken alert path must never roll back the request it exists to announce. **Security bug caught and fixed mid-change:** the new `SECURITY DEFINER` functions inherited Postgres's default PUBLIC EXECUTE grant, so PostgREST was exposing `notify_gem_queue` at `/rest/v1/rpc/` — it takes a job id and kind straight from its caller, making it a forged-alert generator and a write path into `queue_alerts` past its own RLS. Caught by the Supabase advisor, revoked from public/anon/authenticated (triggers are unaffected). Staff workspace also gained `?job=<id>` deep-link handling so the email button opens the right job on the right tab, and the dead leads trigger was dropped. Verified on the live database: probe request plus two back-to-back customer messages raised exactly one `new_request`; a gem reply then a customer reply raised `customer_reply`; status → `in_process` raised `quote_approved` once and a repeat no-op update raised nothing; all three delivered (pg_net 200, `sent_at` stamped); re-POST of a sent alert returned `already_sent` with no second email; wrong secret returned 403; anon RPC returned 401 / permission denied; triggers re-probed after the revoke and still fire; probe data deleted. Staff build live on team.heygem.co.nz (bundle `index-CNsYEY8s.js`). **Not verified:** that the alert emails land in a monitored inbox — see the `LEAD_NOTIFY_TO` card under On Ricky.

Both storage buckets are public — customer documents sit on open URLs
M7securitychat-imagesrating-photos
Found in the `is_gem()` sweep on 2026-07-31, though it is not an `is_gem()` bug — it is worse in one way and better in another. `chat-images` and `rating-photos` are both `public: true`. **Proven, not inferred:** fetching an existing chat-image URL with no apikey and no Authorization header returns HTTP 200 and the file. `chat-images` is where a Gem puts documents into a customer's thread — supplier invoices, statements, job paperwork — and those objects are readable by anyone who ever gets the URL, permanently, with no account. What keeps this off the "stop everything" list: paths are `<uuid>/<uuid>.<ext>`, so they are not guessable, and an anon list call on the bucket returns `[]` (there is no SELECT policy on `storage.objects`, so the bucket cannot be enumerated). So the exposure is "anyone with the URL", not "open directory". Deliberately **not** fixed inside M6: the doneWhen does not need it, and the fix is a real change — flip both buckets private, add owner-scoped SELECT policies, move both apps to signed URLs, and deal with the URLs already persisted in `messages` and `ratings.photo_url`

SEO + analytics
phase-r1M7
Analytics built 2026-08-17, on `dev`, not yet deployed. GA4 (G-4HNCMKRQPF) on the marketing site and the customer app via a shared `@heygem/analytics` package, with cross-domain linking across heygem.co.nz → app.heygem.co.nz so a signup is not attributed to (direct). 17-step buyer funnel instrumented end to end — landing → CTA → auth view → magic link → login → onboarding → sign_up → request start → request sent → quote received → begin_checkout → card required → card saved → quote approved → job completed → purchase → rated — plus the drop-off events that make the gaps readable (`request_abandoned`, `approve_cancelled`, `add_payment_info_abandoned`, `quote_declined`, `magic_link_failed`). Revenue is reported server-side, not from the browser: the card is charged when a Gem marks the job complete, typically with nobody in the app, so a browser-fired `purchase` would miss most of the money and report charges that later declined. `purchase` and `refund` go out from the Stripe path via the Measurement Protocol, keyed on the PaymentIntent id so the sync (`stripe-charge-job`) and async (`stripe-webhook`) success paths cannot double-count. Attribution needs the browser's GA ids to survive to charge time, so `jobs.ga_client_id` / `ga_session_id` are stamped at `create_job` (migration applied to prod 2026-08-17). Verified: real GA4 container loads and transmits (`_ga_4HNCMKRQPF` session cookie advancing), `gtag('get')` returns client_id + session_id, all 6 marketing CTAs and the customer `auth_view`/`auth_mode_switch` events observed in dataLayer with correct params, all three apps build clean, zero new lint errors. Edge functions deployed to prod 2026-08-17 — `stripe-charge-job` v7→v8, `stripe-webhook` v3→v4, both via the Supabase CLI so `config.toml` kept `stripe-webhook` on `verify_jwt = false` (it must stay unauthenticated; Stripe posts without a JWT and the signature HMAC is the gate). `GA4_API_SECRET` confirmed present before deploying. Post-deploy probes: charge-job returns 403 on its shared-secret guard, webhook returns 400 "invalid signature" — both prove the functions boot and the new `_shared/ga4.ts` import resolves; no BOOT_ERROR in logs. Not yet observed end to end: a real `purchase` in GA4 — that needs an actual charge, and faking one would move real money. First live charge confirms it (GA4 Realtime, or a `[ga4]` line in the function logs if it fails).
