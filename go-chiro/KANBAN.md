- **Migration ledger drift — watch for a repeat** `infra` `follow-up` — `supabase_migrations.schema_migrations` was missing its first four migrations, including `001_initial_schema`, because the earliest ones were applied by drizzle push or the dashboard rather than `apply_migration`. Repaired 2026-08-01 (23 → 27 rows), which is what made the staging branch buildable. Anything applied outside `apply_migration` from here re-opens the same hole and silently breaks the next branch, clone or restore.
- **Clinical Stripe calls pin an API version a new account rejects** `M6` `follow-up` — `routes/invoices.ts`, `patients.ts`, `booking-bookings.ts` and `stripe-webhook.ts` all pin apiVersion `2024-11-20`. The live account accepts it because it predates that version, but a newly created account rejects it outright — which is exactly how every shop checkout failed on the staging test account until retail was switched to the SDK's own version. Nothing is broken in production and those files are money-critical, so they were left alone. This will bite the moment M6 onboards a practice on a fresh Stripe account.
- **Pending orders accumulate from abandoned checkouts** `M7` `follow-up` — The order row is written before Stripe is called, deliberately, so a completed session always has a row to match on. The cost is that abandoning the hosted page (or any Stripe error) leaves a `pending` order behind. Harmless — they never paid — but the phase 3 Orders page must filter them out by default, and a sweep that expires pending orders after a day or two would keep the table honest.
- **Drag-to-reorder the catalogue** `M7` `follow-up` — The phase 1 plan said "drag-order" and it was not built.
