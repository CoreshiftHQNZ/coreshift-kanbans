Go-Chiro

Full NZ practice management system, built to replace Splose at a 1–5 person practice.

Reset 2026-08-18. An audit of the code against the live database found roughly 80% of the product built and none of it ever used — 0 invoices, 0 ACC claims, 2 completed sessions and 4 activated accounts, ever. The 3,816 appointments in the database are Splose history the sync pulled in, not work done here. So the bottleneck was never the build; it was that nobody ever ran a day on it, and five milestones were stacked on an unproven base. The app has been taken out of production, the Splose integration deleted (1,478 lines), and the milestones renumbered R1–R7 around one sentence: Luke runs a full clinic day in Go-Chiro with Splose closed. Full plan: docs/ROADMAP.md.

The Three Goals

📅
The diary the practice lives in
Day + week calendar, per-practitioner columns, venue and route-day aware, drag-to-reschedule with conflict detection. Splose's core job, replaced — and mobile-first, because the practice is.
🏥
Bill ACC without leaving the app
One-click Submit to ACC: a compliant invoice PDF emailed to providerinvoices@acc.co.nz with the ACC billing block, plus status tracking. This is what gates cutting the Splose cord.
🤖
The 1 → 3 staff jump
Recalls, waitlist, online intake, reminders and auto-pay do the admin a solo operator does by hand — so hires #2 and #3 are clinicians, not reception.

🔵 This Week

8
A patient record page
R2the big one
There is no patient detail page at all. /a/practitioner/patients is a flat searchable list whose rows are non-navigable divs, and GET /api/patients/:id/history is a literal 501 TODO. Notes, invoices, claims and appointments each live on their own practice-wide screen; nothing joins them per patient. This is the main reason anyone opens a PMS, and R3 is not runnable without it.
Add the auth guard to the history endpoint — before implementing it
R2security
patientsRouter.get("/:id/history") has no isAuthenticated middleware, unlike every sibling route. It returns 501 today so nothing leaks — but it is exactly the endpoint the record page needs, and whoever implements it inherits an unauthenticated patient-history route.
Patients cannot pay an invoice
R2money
The pay modal mounts Stripe Elements with clientSecret: "" and only stores the real secret in child state, so confirmPayment can never succeed. The server side is correct and ACC-aware; it is purely the wiring.
Auto-drafted invoices bill the patient 100%
R2money
Publishing notes auto-drafts an invoice, but the ACC portion is never populated — it can only be typed by hand in the invoice modal. For an ACC practice the default is wrong on every single visit.
A paid invoice can flip back to unpaid
R2money
The payment_intent.payment_failed branch writes the invoice to sent without checking it is not already paid. A late retry or an out-of-order webhook can un-pay a collected invoice and present it for payment again.
Cut pay-at-booking
R2money
Booking creates a payment intent that no client code ever confirms, so it has never worked and nobody has missed it. If it were fixed it would double-charge: the invoice auto-draft only checks for an existing invoice, not an existing booking payment. Recommendation: delete it.
Correct the documentation
R1docs
The README advertises Whisper audio transcription that was deleted. .env.example documents GEMINI_API_KEY for note generation while the code uses Anthropic and reads ANTHROPIC_API_KEY. Eight env vars the server actually reads are undocumented, including SPLOSE_CUTOVER and ACC_INVOICE_EMAIL. Cheapest item on the board, and it is what made the audit necessary.
Nothing ages an invoice to overdue
R2
No job ever transitions sent → overdue, so the Outstanding figure on the payments screen never ages. Draft invoices also sit forever if nobody clicks Send — no reminder, no aging.
