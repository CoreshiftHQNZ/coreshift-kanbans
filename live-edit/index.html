Coreshift Live Edit

Self-serve $100/mo websites the client edits themselves — click any text or image on the live page and change it.

The core Coreshift product: clients get a beautiful site they can edit in place, with unlimited redesigns across a library of theme styles. Edge-native — publishing is a database pointer flip, so go-live is instant; one Cloudflare Worker server-renders every tenant. Cloudflare + Supabase + Stripe + Postmark. Live in production with real customer sites; current focus is proving the money path and hardening security.

Current phase In production · hardening
Next milestone Prove billing end-to-end + close the security gaps P0–P1

The Three Goals

✎
Edit the live page
Click any text or image on your real site and change it. Rich text, links, nav/footer, pages, SEO, plus theme switching across the section + theme library.
⚡
Publish instantly
Publishing flips a pointer in the DB and purges the edge cache, so a change is live in seconds. One Worker SSRs every tenant from the same components the editor uses.
💳
$100/mo, self-serve
Sign up, generate a site from your URL, edit it, go live on a subdomain or custom domain. Trial from first publish, then a Stripe subscription.

🐛 Partner claim fix — the sale now completes (token survives sign-in)
Diagnosed a broken live partner→customer sale (the site never transferred, the partner never saw a payment). Root cause was **front-end only**: the claim page stashed the `?claim=<token>` in localStorage as its *only* way to survive sign-in, but both auth calls (`signInWithGoogle` / `signInWithEmail`) redirected to the **bare origin**. When the customer signed up by magic link and opened the confirmation email on a **different device**, localStorage wasn't there — they landed on the plain dashboard with no claim context, so `claim_prospect` never ran; confused, they built and paid for a *different* site. Fix: redirect to `window.location.href` so the confirmation link returns to `/?claim=<token>` and the claim resumes **cross-device**. Verified the DB side is sound — a rolled-back prod test of `claim_prospect` created the account, moved the site, and set the prospect to `won` cleanly. Once the claim runs, the sold site shows in the partner's dashboard under **Client sites** (Live badge, partner keeps edit access), so "partner sees it's paid" resolves with it. 🔴 Cross-tenant site listing — any signed-in user reads every site row
securitylaunchhgfdssitespublic reads sitesUSING (true)SELECTauthenticatedplanstripe_subscription_idpast_dueanonplan,stripe_subscription_id42501 permission deniedcan_manage_site(id)security definer
Found while walking the partner journey: a brand-new partner account with zero sites and zero memberships showed another customer's site (`hgfds`, *Claimed — not paid*) in their dashboard. **Cause:** `sites` carries an RLS policy `public reads sites` with `USING (true)` alongside a table-level `SELECT` grant to `authenticated`, so RLS never narrows anything for a logged-in user. **Proven:** a partner sees sites belonging to accounts they are not a member of. **Not yet proven, but implied by the table-level grant:** `plan` and `stripe_subscription_id` come through too, i.e. anyone who signs up free could enumerate the customer base and who is `past_due`. *Anonymous access is fine* — `anon` holds column-level grants only, and requesting `plan,stripe_subscription_id` as anon returns `42501 permission denied`, so no billing data is public. **Why it isn't fixed yet:** the blanket policy is what makes shared preview links work for someone who doesn't own the site — precisely the cafe-owner-on-an-iPad path. The fix is to narrow the policy to `can_manage_site(id)` and add a `security definer` RPC for the by-subdomain preview lookup, which must be tested against a signed-out preview link before it ships. **Doing this first, as part of journey #3, since that journey exercises exactly the path at risk.**
